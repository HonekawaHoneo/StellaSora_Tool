# Semantic Component-Driven UI Design

利用者が見分ける必要のある意味から、配置・部品・視覚表現を選ぶ。業務の識別・比較・連続操作を目標とし、美しさ、装飾の少なさ、表示量だけを目標にしない。

## 説明をUIの本文へ置かない

本文の補足説明はゼロに抑える。「必要な部分は文字で説明する」は説明文の追加・保持を勧める指示ではない。説明が必要に見える箇所はUIの意味設計が機能していないと判定し、次の順で直す。新しく足す文だけでなく既存の説明も対象にする。

項目名と説明は別である。名称・実データ・値・単位・短い操作名はオブジェクトの意味そのものであり、保つ。ラベルを消して曖昧なアイコンにする必要はない。一方、文章をlabel/statusというroleで申告しても説明文である事実は変わらない。

アプリの用途から自明な説明、項目名や操作で既に伝わる説明は削除する。Q&Aやツールチップへ移し替えない。「初見だから」「あると親切」「機能の事実として正しい」「以前からある」は保持の理由にしない。

| 順序 | 解決すること |
| --- | --- |
| 1. レイアウト・配置 | 関係、読み順、操作距離、表示範囲、必要な情報の見え方をまず考える。グルーピング、展開・折り畳み、stickyによる固定表示は例であり、必須手法や検討範囲の上限ではない |
| 2. オブジェクト自体のデザイン | 配置で解決できない区別を、部品の種類、形、見た目、サイズ、短い項目名・操作名、状態表現で解決する |
| 3. 色分け | それでも残る区別に、意味と一致する色を使う。色だけを識別手段にせず、配色の説明文も足さない |

各段階で解決できれば、後の手段を追加しない。すべての場面へ折り畳み・sticky・色分けを適用する指示ではない。

Q&Aの追加は最終手段とする。上の順に検討しても伝えられず、欠けると利用者が目的の操作を完了できない具体的な情報が残る場合だけ、既存の入口を優先して必要最小限を扱う。その情報と各代替が成立しない根拠を既存の設計・copy判断へ記録する。「詳説だから」だけでは新設・追記しない。自明な説明を保存する場所や、配置の検討を省く近道にしない。

| 本文へ置かない文 | 先に直すもの |
| --- | --- |
| 「ここに目標コインを入力してください」 | 入力欄の「目標コイン」というラベルで表す |
| 「＋と−で回数を調整できます」 | 回数と増減ボタンを一組の操作オブジェクトとして配置する |
| 「目標コインは保持します」 | 目標と回数操作の関係を配置で明確にし、実処理に合う「回数をリセット」という操作名にする。説明は削除し、Q&Aにも移さない |
| 「保存に失敗しました。ブラウザー設定を確認してください」 | 対象に近い「保存失敗」という状態と実行可能な回復操作で成立させる。手順のQ&A追加も上記の最終手段の条件で判断する |
| 「橙色は再抽選、紫色は音符です」 | 見出し・所属・オブジェクトを明確にし、配色の解説で意味を補わない |

配置・ラベル・色を変えた後は文言を再判定する。前の曖昧なUIで必要だった説明を、新しいUIにも惰性で残さない。

設計・レビューの判断理由は工程成果物へ記録し、UIへ実況や制作意図として表示しない。

## 既存工程への接続

AGENTS、共通工程、対象アプリのデザインシステムを最初に確認する。poteto-modeが進行、ponytailが設計・実装、ponytail-reviewが独立レビューを担当する。このSkillはUIの判断だけを補い、要件確認・承認・工程管理をもう一式作らない。

作成前に[原則と検証の対応表](references/principle-checks.md)を使う。新規UI作業は`.harness/ui-principles.md`のv3契約（既存v1/v2は明示移行時だけ変更）を接続してから変更単位を開始する。原則を読んだこと、機能試験が通ったことだけを、原則を満たした根拠にしない。

UIのレイヤーは構造階層、視覚的優先順位、奥行きを区別する。内部アーキテクチャやファイル構成のレイヤーではない。

| 作業 | 既存手段との関係 |
| --- | --- |
| 外観維持・スタイル移行 | Visual parityを使い、基準画像への一致を検証する |
| 新規設計・意味の改善 | 意図した外観差分を評価する。Visual parityの差分ゼロを要求しない |
| 判断のための試作 | Prototypeを再利用し、最初にレイアウト骨格を可視化する |
| 実装の簡素化 | Subtract Before You Addを適用する。必要な視覚表現の削除理由にはしない |

## 6つの処理

### 1. 意味と識別要求、本文の説明を除去

既存の部品一覧、トークン、画面、確定済みルールを調べる。基本的役割、対象・操作、状態、重要度、危険性、配置文脈、関係性を分離する。何を表示するかに加え、利用者が何を見分ける必要があるかを列挙する。

変更範囲をnone/local/sharedにする。小変更は同役割部品と対象状態を確認し、共有部品・トークン変更は利用先へ広げる。環境から分かることは調べ、結果を大きく変える未決定事項だけ確認する。

ワイヤーフレームや配色の前に全表示文を確認し、オブジェクトの名称・値・単位・操作ラベルと、説明・重複・装飾を分ける。説明を削除できる意味構造へ直す。既存文言をすべて確定仕様と扱わない。

### 2. レイアウト骨格

最初の視覚成果物はワイヤーフレーム。prepareより先に変更単位のinputsへ保存し、実装前のhashを固定する。情報領域、所属、親子、比較軸、主操作の位置に加え、作業中に何が見え、何を必要時に開き、スクロール中に何を参照できるかを考える。グループ分けだけで配置の検討を終えず、最終色や個々の部品の外観を先行させない。

### 3. 部品選定

既存部品 → 既存部品の組み合わせ → 定義済みバリエーション → 新しい意味・役割の部品提案の順に検討する。再利用先が情報の意味を表せなければ、適合する部品や組み合わせを選び直す。

階層探索、属性比較、単純な列挙、独立した対象の要約を区別してツリー・テーブル・リスト・カードを選ぶ。同じ基本操作に対象別の新部品を増やさない。新設提案には意味、既存との差異、使用条件、再利用範囲を示す。

### 4. 意味から視覚表現を決定

色、文字、アイコン、形、余白、境界線、影は役割・状態・重要度から既存のSemantic Tokensを選ぶ。外観が似た別用途のトークンで代用しない。意味ごとに採用する手掛かりと、省略する手掛かりの理由を記録する。

色も同じ基準で判定する。選ぶ前に対象・所属・状態・重要度・危険性のどれを区別する色かを決め、意味が同じものは同じtokenへ結ぶ。根拠のないアクセント色や領域ごとの塗分けを増やさない。色の意味を説明文で補わなければ分からない場合は、配置・オブジェクト・状態表現の設計不備として見直す。色だけで情報を伝えず、色を外しても所属・操作・状態を識別できる構造を保つ。

構造階層が必要なら親子・兄弟・所属が見える表現を与える。選択、フォーカス、無効、危険性も必要な区別を保つ。全要素をカード・枠・影で囲う必要はない。

### 5. 密度と過不足を調整

不要な余白・見出し・説明・装飾は整理し、不足する区切り・階層・状態・操作の手掛かりは追加する。同じ条件で情報識別、比較、発見、操作手順、スクロールを確認する。表示行数や装飾数だけで採点しない。

業務一覧は作業領域に比較可能な行・列と操作を配置する。既存の行高・余白・横幅を引き継ぐ。密度が未定義なら文字の行高と部品寸法を先に置き、読み取り・誤操作防止・所属の区別に必要な余白を足して決める。判断記録には行高、操作対象寸法、上下余白の用途を残す。外周余白も作業領域と隣接領域の区別から決定する。

見える印の寸法と、実際に操作を起動する領域の寸法を別々に決める。小さなタスク用ユーティリティでは、本文に釣り合う控えめなnative checkboxから始め、必要なら関連するlabelの操作領域を広げる。例えば20pxの印と44pxの操作可能なlabelは別の設計値である。20pxは全製品共通の上限ではない。既存の大きなコントロール体系、明示された弱視への配慮、ユーザーの寸法指定には、その根拠に合うサイズを選ぶ。

「モバイルだから」「タスクが3件だけだから」「44pxのタッチ領域が必要だから」だけで、見えるチェック印まで44pxへ拡大しない。周囲の文字に対する支配性を確認し、小さい印と同じ操作領域で目的を満たせるか比較する。測るのは無関係な外枠の余白ではなく、その位置への入力が意図した操作を本当に起動する範囲である。通常ボタンは見える面と操作面が同じでもよい。wrapperの新設を必須にしない。

文字を次に分類して扱う。

文字サイズ、行高、行の高さ、操作対象寸法、余白は、用途と検証できる期待値を実装前に決める。小さな操作アプリを暗黙にランディングページの構成へ変えず、控えめな見出しと通常の本文から始める。既存の基準と利用目的を優先し、文字を一律に縮小しない。読みやすさと操作対象の大きさは別々に確保する。

| 文字の目的 | 判断 |
| --- | --- |
| 名称・実データ・値・日時・単位 | 作業に必要な情報を保つ |
| 操作名・項目ラベル | 対象・項目・操作を識別する名前を保つ。項目名と説明を混同しない |
| 状態・危険性・アクセシビリティ情報 | 状態名・対象・操作・制約を識別できる形で保つ。背景や手順を自動でQ&Aに追加しない |
| 新旧すべての補足説明 | 自明・重複なら削除。残る問題は配置→オブジェクトの見た目・サイズ→色の順で直し、Q&Aは上記の条件を満たす最終手段に限る |

アイコンが曖昧なら配置を先に見直し、既存の文字付きバリエーションや短い操作名などオブジェクト自体で識別できる形にする。何でもツールチップで解決しない。削った説明をtitle属性やhoverへ移さず、見える項目名や操作の発見をツールチップ・aria-labelだけに任せない。アクセシブルな名前は保ち、ツールチップは補助にとどめる。

キャッチコピー、励まし、同じ意味の言い換え、補足文を雰囲気づくりのために足さない。空状態は件数と追加操作、完了状態は完了数・チェック状態、エラーは短い状態名と実行可能な回復操作で示す。同じ事実を既に伝えているなら説明文や状態メッセージを重ねない。操作説明を置く前に、0件と追加オブジェクトで成立させる。「空状態・全完了のメッセージを表示」という要件だけでは、励ましやキャッチフレーズを加える許可にならない。

全表示文に、roleから独立したpurpose、実際の根拠source_ref、除去・短文化したときに失う情報と代替案、重複を残す理由を記録する。statusやlabelというroleでも必要性の説明を省略しない。実装そのもの、後付けの理由、広い要件IDを文言指定の代用にしない。実画面から取得した全表示文一覧を照合する。

新規object-firstの非object文言例外は、本人が正確に指定した原依頼をauthorization_refのoriginal_brief・exact_textで参照し、scopeのpurpose・surface・target・case_idsを当該文言の全表示範囲に一致させる。一般的な状態メッセージ要件、親しみやすさ、文章制作の委任を説明文の制作許可へ読み替えない。本人の新しい明示指示が確定条件を変える場合は、その原文と対象範囲を記録して影響する上流からreopenし、実装前に再固定する。単語ごとの再承認は追加しない。詳細な形式は`.harness/ui-principles.md`を使う。

copy_policy未指定の旧v3に限り、原依頼の明示的な文章制作委任をcommissioned_copyで記録できる。原指示とpurpose・対象状態を実装前に固定し、生成文の逐語再承認は求めない。新規object-firstへこの経路を持ち込まず、ui-principles.mdの現行契約を使う。

### 6. 機械検査と実画面レビュー

既存lint/tests、ブラウザ、必要なアクセシビリティ検査を使う。実画面の通常・選択・フォーカス・無効・展開・空・エラー等から該当する状態を確認する。異なる幅、対応テーマ、拡大も変更範囲に応じて確認する。折り畳みや固定表示を採用した場合は、必須操作・エラー・フォーカスの発見と到達、狭い幅やスクロール時の遮蔽も確かめる。

独立レビュアーは原依頼と実画面・操作を先に見て、親子、所属、重要操作、状態、危険性を答える。期待値を見る前に「小さな印＋同じ操作領域」と「状態の事実＋短い次の操作」で十分かを検討し、その後設計と照合する。見える印の過剰な強調や不要な励ましが作業用の簡潔さに反する場合は修正を要する指摘として扱う。モバイル・件数の少なさ・一般的なメッセージ要求を理由に、任意の好みへ格下げしない。明示的な大きさ・弱視要件・正確な文言指定など、判断を変える根拠も同じ基準で確認する。文章制作の委任はcopy_policy未指定の旧v3に限って扱う。

設計された範囲・copyのpurpose・出典・必要性・重複の理由自体を評価し、期待値が不適切なら実測が完全一致でもrequest_changesとする。v3ではmeasurements/controls/copyの各IDに根拠・理由と妥当性判断を残す。purposeの誤分類や原依頼を装った参照は機械的な文意解析に頼らず、独立レビューで指摘する。過剰と不足を別々に記録する。機械検査・画像差分の成功を、意味の分かりやすさの証明にしない。

本文に補足説明が残る場合は、必要性の作文で合格にせず、配置→オブジェクトの見た目・サイズ→色の順で修正を要求する。配色も解説文を使わず意味が伝わるかを判定する。Q&Aの新設・追記やツールチップへの移動も確認し、不要な説明を隠しただけでは合格にしない。レイアウト・寸法・コントラストだけの確認でUIレビューを完了せず、変更後に文言を再評価する。

## 成果物と証跡

0.17.0の新規作業では対象の`.harness/execution.md`に従い、このSkillとUI実装担当の実読出し・適用先を現在入力のtokenへ結ぶ。新UIはv3/enforceとcopy_policy="object-first"をnew --ui前に接続する。後からUI変更が判明したstrict作業はreopen discovery --uiへ戻す。型付きの全4surface、Q&Aの配置・オブジェクト・色の代替不成立を示す実証跡、全copyごとの独立した判断は`.harness/ui-principles.md`の現行フィールドを使う。本文だけでなくツールチップ等への説明の移動も照合する。CLIの参照検査を意味判断の証明と扱わない。

本番変更ではプロジェクトの任意ui設定を確認し、`.harness/ui-design.md`の契約を使う。UI入力のglob、既存定義参照、実行可能なcheckを登録する。設定がなければ既存構成を調査して接続し、未接続を検証済みと扱わない。

v2/v3では10原則ごとの判断・参照・caseをdesign.ui.principlesへ記録する。実装前に文字・寸法・状態・操作の期待値をdesign.ui.casesへ固定し、実行時は同じcaseの実測ファイルを参照する。独立レビューはすべての原則について実画面の観測、過剰、不足を記録し、適用除外と継承の根拠も確認する。v3は見える寸法と起動領域、全copyの根拠、期待値自体の妥当性判断を追加する。v1/v2の既存証跡にv3の保証を遡及しない。

既存UIは実装前に既存ブラウザ手段でbefore画像を取得する。`python3 .harness/ui_contract.py prepare <id> --before <JSON>`でRegistry参照と画像の指紋を保存する。design.json.uiに意味→部品・表現→画面シナリオの対応を記録する。既存のrunで実画面証跡を生成し、review.json.uiは特定の成功receiptへ結び付ける。

共有ルールを変える場合は、既存定義の見落としと単純な実現方法を再確認し、理由・差分・影響先・実際の承認を残す。確定後に正本へ反映する。既に承認された内容を再承認待ちに戻さない。

使い捨て試作に実アプリのRegistryがない場合は、与えられた部品情報と仮定を暫定参照として残す。本番の検証合格・正本更新とは扱わない。ブラウザ担当が別なら必要な画面状態を引き継ぎ、未確認を明示する。

## 例: 深いタスクツリー

親子・兄弟・現在位置、開閉可能性、選択、フォーカスを識別要求にする。既存ツリーを優先し、なければ既存の行と開閉部品の組み合わせを検討する。フラットなリストをそのまま流用しない。

インデント、展開アイコン、選択とフォーカスの区別から始める。深い階層で親を追えなければガイドライン等を追加する。十分に追えるなら線を増やさない。操作付きツリーでは実際の親子構造とARIA、矢印キー、選択とフォーカスを整合させる。読み取り専用の階層まで一律にARIA treeにしない。

## よくある誤り

| 問題 | 確認すること |
| --- | --- |
| コンパクトさのため必要なラベルを省略 | 初見で操作と対象を識別できるか |
| 既存リストで階層を文字だけ表示 | 親子・兄弟・現在位置が見えるか |
| 影を消して階層も消失 | 構造階層・優先順位・奥行きを分けたか |
| 画像差分ゼロを改善の条件にする | 今回は外観維持か意味の改善か |
| すべてを新しい外観へ置き換える | 既存の正しい意味表現を変える理由があるか |
