# UI Implementation Harness

UIは意味を持つ部品をコンテナへ配置し、操作と状態を接続して構成する。
既存の共通工程の中で、UI固有の判断と検証対象だけを補う。

## 最初に読むもの

プロジェクトのAGENTS、共通のprotocol/skill-compatibility、現在の要件・設計、
UI Designの確定事項を読む。作成中のDesignは合意済みの責務・振る舞いを参照し、
未確定部分を区別する。確定済みの意味・視覚階層・密度を実装都合で変えない。

現状の説明文の存在を確定仕様と扱わない。用途から自明な説明は削除し、項目名・実データ・単位・短い操作名は保つ。項目名と説明は別である。

説明が必要に見える問題は、レイアウト・配置全般→オブジェクト自体の見た目・サイズ→色分けの順で解決し、解決した段階で止める。グルーピング・展開折り畳み・stickyは配置の例であり、必須手法や検討範囲の上限ではない。配置で関係・読み順・操作距離・情報の見え方を考えてから、部品の種類・形・サイズ・操作名・状態表現を見直す。色は意味に対応させ、色だけや解説文に頼らない。

Q&Aは、この順でも伝えられず、欠けると目的の操作を完了できない具体的情報が残る場合の最終手段に限る。その情報と各代替が成立しない根拠を既存の設計・copy判断へ記録し、既存の入口を優先する。「詳説だから」だけで新設・追記しない。自明な説明を移さず、何でもツールチップで解決しない。title属性やhoverへ説明を隠すだけでは解決にせず、見える項目名・操作名とアクセシブルな名前を保つ。

label/statusというrole名で長い説明を温存しない。設計・レビューの判断理由は工程成果物へ記録し、UIへ実況や制作意図として表示しない。

## 変更する範囲を決める

1. 対象部品の意味、コンテナ、全操作入口、状態所有者、イベント、実処理接続を確認する。
2. 同じ意味の操作は共通フローへ接続し、入口の対象IDを起動時に確定する。
   応答と画面の寿命を対応づけ、取消・再表示・遅延応答・二重送信を扱う。
3. 外観、表示構造、UI制御、実処理接続を論理的に分ける。
   共通化は同じ変更を適用すべき範囲まで。認可・検証・監査・障害隔離の境界は維持する。
4. 共有操作・状態・横断依存・移行が変わる場合は
   [UI契約](references/ui-contract.md)の該当項目を更新する。
   役割・変更理由・状態・依存で分割し、行数や画面階層を分割の絶対条件にしない。

## 変更に応じた確認を選ぶ

| 変更 | 必要な確認 |
| --- | --- |
| 表示文・ラベル・説明 | 自明・重複の説明は削除。残る問題は配置→オブジェクトの見た目・サイズ→色の順で直す。項目名・データ・単位・操作名を保ち、Q&A・ツールチップへ不要な説明を移していないか再確認する |
| 角丸など外観のみ | 既存決定を参照し、対象トークンと利用側を確認。既存のクリック・キーボード操作とfocusも実際に維持確認する。新しい状態設計や大規模な試験は不要 |
| 配置・共通部品 | 他画面の利用、起動、状態、通知を逆引き。実入力で伝播・hit test・Tab順序・focus・drag等を確認。折り畳み・固定表示を採用した場合は必須操作・エラー・focusの発見と到達、狭い幅やスクロール時の遮蔽も確かめる |
| 操作・状態・接続 | 共有フローの確認計画には、各入口の対象、成功・失敗、送信前取消、二重送信、遅延応答を列挙する。独立境界も確認し、一般テストは既存の担当へ |
| HTMLモック移行 | 意味・構造・操作・遷移・デザイン参照を対象技術へ対応づけ、接続ごとの仮実装・未実装と検証範囲を引き継ぐ |

## 標準方式と複雑化

新しい実現方式、標準機能の独自再実装、補正や再発の増加、過剰な状態同期、
無関係な部品への波及では[標準方式の検証](references/standard-path.md)を行う。
再現・原因分析は利用可能なsystematic-debugging等の既存担当へ接続し、本文を複製しない。

## 既存工程へ戻す

0.17.0の新規作業では`.harness/execution.md`の現在入力・実読出し・実ファイル適用先へ接続し、UI設計・実装の両担当を使う。v3/enforce・copy_policy="object-first"をnew --ui前に固定し、後からUI変更が判明したstrict作業はreopen discovery --uiへ戻す。全4surfaceの型付きcopyと、Q&Aの配置・オブジェクト・色の代替不成立の実証跡、全copyの独立判断は`.harness/ui-principles.md`の現行契約を使う。説明を別surfaceへ移すだけで合格にしない。

実行可能なBrowser/Playwright経路を一つ選び、操作と可視結果を確認する。
技術別Skillは対象技術と規則が合う場合だけ使う。追加導入・権限は依頼の範囲に従う。
要件と検証IDを既存design.jsonへ対応づけ、run/check/advanceと独立レビューを使う。
操作不可・未実装・未検証はそのまま残し、画像やWebの成功でnative機能を合格にしない。
原則を実装と検証へ結ぶときは[検証への接続](references/principle-checks.md)と`.harness/ui-principles.md`を使う。v2/v3ゲートは原則・caseの網羅と証跡内の実測値を検査する。v3は見える印の幅・高さと実際に操作を起動する領域の幅・高さを別caseで測り、actionへ結ぶ。小さなnative印と広い操作可能なlabelから始め、無関係な外枠の寸法を操作領域として報告しない。全copyの目的・出典・代替・重複理由を引き継ぐ。複雑化の妥当性、意味の伝わり方、未申告の操作がないかは独立レビューでも確認する。

新規object-firstの非object文言例外は、本人が正確に指定した原依頼をauthorization_refのoriginal_brief・exact_textで参照し、scopeのpurpose・surface・target・case_idsを当該文言の全表示範囲に一致させる。一般的な状態メッセージ要件、親しみやすさ、文章制作の委任を説明文の制作許可へ読み替えない。本人の新しい明示指示が確定条件を変える場合は、その原文と対象範囲を記録して影響する上流からreopenし、実装前に再固定する。単語ごとの再承認は追加しない。詳細な形式は`.harness/ui-principles.md`を使う。

copy_policy未指定の旧v3に限り、原依頼の明示的な文章制作委任をcommissioned_copyで記録できる。原指示とpurpose・対象状態を実装前に固定し、生成文の逐語再承認は求めない。新規object-firstへこの経路を持ち込まず、ui-principles.mdの現行契約を使う。

## 間違えやすい境界

表示状態の画像と実操作、共有画面と全画面共通の可変状態、似た外観と同じ実処理を区別する。
小さな外観変更では既存契約への差分参照で足りる。同じヒアリングや承認を別工程で繰り返さない。
